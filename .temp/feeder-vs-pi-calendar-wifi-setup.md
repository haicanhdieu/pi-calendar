# feeder vs pi-calendar: Wi-Fi setup / admin web server comparison

## Summary

feeder's AP-setup and scheduler web servers are trivially simple: one `uasyncio.start_server` callback per surface, ~35-115 lines each, building one small HTML string per request with plain concatenation, no CSS/JS blobs, no lazy-import machinery, no incremental per-tick parser, no bounded-byte streaming, and no dedup'd error-log state. They allocate a burst of memory per request (whole request buffer, whole response string) and then let the socket close release it immediately — the GC never needs to compact/track much because nothing lives across ticks.

pi-calendar's `SetupHttpServer` (`src/device/web/server.py`) and `coordinator.py` implement a much more sophisticated, "heap-safe by design" model: a hand-rolled incremental parser (`IncrementalHttpParser`) that survives across many `tick()` calls, bounded per-tick read/write (`HTTP_PER_TICK_BYTES = 512`), held-client state machine for async KDF work, lazily-imported page-content modules with large embedded CSS/JS strings, and structured failure/dedup/retry bookkeeping. This sophistication is exactly what's supposed to prevent the MemoryError problem — but it is also a large amount of code and state that must itself be constructed and kept live (parser objects, `_Client` slots, outbox buffers, session tables, KDF job objects), and the failure paths (`_web_failures_emitted` dedup bug) can silently swallow a first failure and never retry visibly. feeder simply never accumulates this much long-lived object graph or code-import surface, so it never encounters the same failure modes — it doesn't need to, because its pages are trivial and disposable per-request.

The core structural difference isn't "feeder is more heap-safe," it's "feeder's problem is much smaller." pi-calendar is trying to serve much richer pages (two-screen SPA-like flow with JS, live SSID scan/fetch, sessions/login/settings, PBKDF2 KDF) through a full incremental streaming HTTP implementation, which is inherently a bigger, fragmentation-prone memory workload on the same 190KB heap. The fix is not to imitate feeder's simplicity 1:1 (the product requirements differ) but to borrow its specific memory discipline: smaller inline strings, no embedded JS state machine reconstruction cost per import, blocking-per-request-but-short-lived allocation pattern where possible, and — most concretely — fixing the dedup bug that hides the recurring failure and re-examining whether the current CSS/JS payload sizes (page_setup_content.py's `_CSS`/`_JS` are ~1.8KB and ~4.3KB of literal source respectively) are worth precompiling/shrinking further.

## How feeder does it

- **ap_webserver.py / scheduler_webserver.py**: one `async def handle_client(reader, writer)` registered via `uasyncio.start_server`. uasyncio's own event loop handles accept/read scheduling — there is no hand-rolled non-blocking accept/read/write state machine, no per-tick byte budget, no bounded incremental parser. `reader.read(1024)` blocks (cooperatively, via asyncio) until data or EOF; the whole request is parsed synchronously from one buffer using `str.split`/`re.search`.
- **HTML building**: `ap_webserver.py`'s GET response is one f-string-free concatenation of a handful of short literal fragments (~10 lines of HTML, no CSS, no JS). `scheduler_webserver.py`'s response is built by repeated `html +=` concatenation in a loop over schedules — more per-request garbage than the AP page, but still just plain text with inline `style=` attributes, no embedded stylesheet or script block at all.
- **No lazy imports of page modules**: everything needed to build a page (regex, json, url_helper) is imported once at module load, eagerly, at the top of the file. There's no separate "page content module" split — because there's so little content, splitting for import-time footprint isn't a concern.
- **gc**: no explicit `gc.collect()` calls anywhere in the 5 files read. No `gc.threshold()` tuning. Memory management is entirely implicit — each request's transient buffer (request bytes, decoded string, response string) becomes garbage as soon as the handler returns and `await writer.aclose()` runs, and the small heap footprint of these transient objects (client requests are ≤1KB, responses are a few hundred bytes to a few KB) means fragmentation risk is low even without proactive collection.
- **No precompilation**: no `mpy-cross` step referenced in these 5 files.
- **Error handling**: a single `try/except Exception as e: print(...)` around the whole handler body, with `finally: await writer.aclose()`. No named/coded failure taxonomy, no dedup, no retry scheduling — if something throws, it's logged plainly and the connection is closed; the *next* connection gets a fresh attempt with no memory of the previous failure.
- **Server lifecycle**: `main.py` calls `await start_web_server(ip)` (or the AP variant) exactly once at boot, synchronously in the startup sequence, and never revisits/reconstructs it. There is no "server construction can fail, retry later" path at all — if `asyncio.start_server` throws, the whole `main()` coroutine dies (caught only by the top-level `try/except KeyboardInterrupt` in the `__main__` block, which doesn't even catch generic `Exception`).
- **Concurrency model**: cooperative via `uasyncio`, but the web server coroutine is one of only a handful of tasks (`monitor_button`, `run_scheduled_jobs`, blink LED) — no bounded per-tick byte budget is needed because `uasyncio` itself multiplexes the blocking-looking `await reader.read()` calls.

## How pi-calendar does it

- **src/device/web/server.py — `SetupHttpServer`**: a bespoke non-blocking, bounded, single-step-per-`tick()` server. `ensure_listening()` constructs and binds/listens on a raw non-blocking socket; `tick()` does at most one accept, one write-drain, or one read per call, capped at `config.HTTP_PER_TICK_BYTES` (512 bytes) per socket op. Each connection is a `_Client` object (`__slots__` for 7 fields) holding an `IncrementalHttpParser` instance that must persist across many ticks while a slow/partial request streams in. This is a much larger and longer-lived object graph than feeder's "one coroutine + two local buffers per request."
- **HTML building**: pages are built as large literal string concatenations in `page_setup_content.py` (313 lines, ~1.8KB `_CSS` + ~4.3KB `_JS` string constants), `page_login_content.py`, and `page_settings_content.py`. Building a page allocates one big final string (via chained `+`, matching CPython/MicroPython's usual quadratic-ish concatenation cost for many small pieces) plus the encode-to-bytes step in `pages.http_response`. `server.py`'s own comment (line 428-429) explicitly documents having already fixed one bug where `outbox[offset:]` "duplicates the entire page response on the Pico heap" — evidence this exact failure mode (large transient duplicate allocations) has already bitten this codebase once.
- **Lazy imports**: `pages.py` (the dispatcher) imports each of the three content modules only inside the function that needs it, and `server.py._dispatch_config` explicitly imports `pages as config_pages` and the router only "after a browser reaches the station-online surface" (comment, line 347-348) — an explicit design decision to avoid ever pulling admin-page code into RAM during setup-AP mode. This is strictly more careful than feeder, which has no equivalent problem to solve (feeder has no separate large admin/config surface).
- **gc**: `coordinator._get_http()` calls `gc.collect()` before constructing the HTTP server; `server.py._dispatch_setup` calls `gc.collect()` before building the scan response; `_scan_ssids` in coordinator.py also collects before scanning (per AGENTS.md rule). There's a `config.WEB_HEAP_CHECKPOINTS`-gated `_heap_checkpoint()` for serial diagnostics. This is much more explicit GC management than feeder's "never call it" approach — a sign the team already knows this is a fragile boundary, but it's still not solving all cases (production evidence: MemoryError still happens intermittently).
- **Precompilation**: `tools/deploy.py` mpy-cross-precompiles several modules (per background) — feeder has nothing equivalent, but also doesn't need it given its module sizes.
- **Error handling / dedup bug**: `coordinator._web_failure(phase, ...)` only emits the log/event the *first* time a given `phase` string is seen (`if phase not in self._web_failures_emitted`), and only clears that phase via `_web_recovered()`. If recovery never happens (the actual failure mode reported), the phase stays in `_web_failures_emitted` forever and every subsequent identical failure is silently swallowed — a real regression vs. feeder's "log every single failure, no memory across requests" approach. This is a diagnosability gap unique to pi-calendar's more stateful design, already flagged as known/unfixed.
- **Server lifecycle**: `_get_http()` is re-entrant and retryable — if construction throws `MemoryError`, `self._http` stays `None` and `_tick_setup_ap`/`_tick_station_config` will retry every `HTTP_RETRY_MS` (2000ms) tick after `gc.collect()`. This is more resilient in *design* than feeder (which has no retry path at all), but in *practice* the retries can apparently loop without ever succeeding for 60+ seconds, and the loop's own retry cadence (every 2s, with a `gc.collect()` each time) is itself extra allocation/collection pressure layered on top of an already-fragmented heap.
- **Concurrency model**: a synchronous `tick()`-driven cooperative loop (not `uasyncio`), invoked presumably once per outer app loop iteration, doing at most one bounded unit of I/O work per call — deliberately avoiding `uasyncio`'s own allocation overhead, but requiring all of parsing/session/KDF state to be manually kept alive across ticks in Python objects rather than living on a coroutine's stack (which uasyncio/MicroPython can garbage-collect more predictably once a coroutine completes).

## Key differences

| Dimension | feeder | pi-calendar |
|---|---|---|
| HTTP engine | `uasyncio.start_server` + blocking-style `await reader.read()` | Hand-rolled non-blocking socket state machine, bounded per-tick bytes |
| Request lifetime | One coroutine per request; state dies with it | `_Client` objects + `IncrementalHttpParser` persist across many ticks |
| Page size/complexity | No CSS, no JS, ~10-50 lines of literal HTML | Full CSS (~1.8KB) + JS (~4.3KB) SPA-like page per surface, 3 separate large content modules |
| String building | Plain `+`/`+=` concatenation of small literals | Same plain concatenation, but over much larger literals producing a bigger single final string held in `outbox` |
| Lazy imports | None — everything eager at module top | Deliberate: content modules, router, config pages, KDF, sessions all imported lazily and only on-path |
| gc.collect() calls | Never | Multiple explicit call sites (`_get_http`, `_dispatch_setup` scan, `_scan_ssids`) |
| Precompilation | None | mpy-cross via `tools/deploy.py` |
| Failure handling | Log-and-drop per request, no state | Named phase taxonomy + retry scheduling + **dedup bug that can permanently swallow repeat failures** |
| Server construction | Once at boot; unrecoverable if it throws | Retryable every `HTTP_RETRY_MS`, but retries can loop indefinitely without succeeding |
| Held/async state | None — nothing waits across ticks for a slow background job | `_held_client` / KDF job objects intentionally span many ticks (PBKDF2 is chunked at `KDF_ROUNDS_PER_TICK = 200`) |
| Response transfer | Single `writer.awrite(response)`, whole buffer at once (uasyncio handles chunking) | Explicit bounded `chunk = outbox[offset:offset+512]` per tick to avoid one giant `send()` and avoid the previously-fixed "duplicate whole response" bug |

The single largest structural fact: **feeder's biggest response payload is a few hundred bytes of HTML with zero embedded assets; pi-calendar's smallest setup-page payload is several KB of HTML+CSS+JS.** No amount of streaming/bounding logic changes the fact that building that string still needs one contiguous allocation for the final `body_bytes` (in `pages.http_response`) before it can be chunked out — the bounded per-tick *write* doesn't bound the *build*. That single build-time allocation, repeated after gc has already fragmented the 190KB heap from CYW43/lwIP + parser/session objects, is the most likely remaining MemoryError trigger, and it is architecturally impossible for pi-calendar to shrink to feeder's level without shrinking the actual page content.

## Ranked recommendations

1. **(High impact / low effort) Fix the `_web_failures_emitted` dedup bug now.** `coordinator._web_failure()` (lines 128-144) never re-logs a phase once added to the set unless `_web_recovered()` clears it, but a failure loop that never reaches the "recovered" call path leaves the operator blind for the entire outage. Minimal fix: also log (at reduced frequency, e.g. every Nth retry) even when the phase is already in the set, or store a last-emit timestamp instead of a one-shot boolean and re-emit every `HTTP_RETRY_MS * K` ticks. This doesn't reduce MemoryError frequency but is required before any of the harder fixes below can be verified with serial evidence — right now a silent repeat failure is indistinguishable from "no error occurring."

2. **(High impact / medium effort) Shrink the single contiguous allocation each page build produces.** `pages.http_response()` (pages.py lines 29-65) and each `*_page_html()` in `page_setup_content.py`/`page_login_content.py`/`page_settings_content.py` build one big final `str`, then `.encode("utf-8")` it (a second full-size allocation), before any chunked send happens (server.py `_write_client`, lines 424-461). Options ranked by ease: (a) trim `_JS`/`_CSS` in `page_setup_content.py` — it's the largest page and includes a full two-screen SPA controller; feeder proves a much plainer, server-rendered-per-state page (no client scan/fetch, no toggle JS, plain multi-page navigation via full reloads) is sufficient for a setup flow and would cut this module's string size by more than half. (b) Move CSS/JS to two static, cacheable `.css`/`.js` served-once-and-cached-by-browser assets instead of inlining into every HTML response — a request that's already authenticated/rescanned doesn't need to resend 4KB of unchanging JS. (c) At minimum, encode+build incrementally into a `bytearray` via `.extend()` at each literal boundary instead of `+`-concatenating strings, to avoid holding both N partial-concatenation intermediates and the final string simultaneously (MicroPython's `+` on immutable `str` can retain more intermediate garbage than an explicit buffer approach before the next `gc.collect()` runs).

3. **(Medium impact / low effort) Call `gc.collect()` immediately before building the page string, not just before importing/scanning.** Currently `_get_http()` and `_dispatch_setup`'s scan branch collect, but the actual largest allocation — building `setup_page_html()`/`response_setup_page()` inside `pages.response_join_failure`/`response_setup_page` (pages.py lines 82-83, 149-160) called from `server._dispatch_setup`/`_dispatch_config` — has no collect immediately beforehand. Given AGENTS.md's own rule ("a successful gc.mem_free() reading does not prove a later allocation will succeed"), add a `gc.collect()` call directly in `server.py` right before `client.outbox = pages.response_setup_page(...)` (and the equivalent login/settings paths) so the heap is maximally compacted at the single largest allocation point in the request lifecycle, rather than several function calls/tick-cycles earlier where other work (parsing, routing) can re-fragment it in between.

4. **(Lower impact / higher effort, longer-term) Consider whether `uasyncio` (like feeder) rather than the hand-rolled bounded-tick state machine would actually reduce peak heap pressure**, since feeder's coroutine-per-request model lets MicroPython's GC reclaim an entire request's working set the instant the coroutine returns, with no long-lived `_Client`/parser objects spanning ticks. This is a large refactor and cuts against pi-calendar's explicit reasons for the current design (bounded, non-blocking, single-thread-safe with KDF chunking) — not recommended unless recommendations 1-3 prove insufficient after device testing, but worth recording as the most feeder-like structural option if the intermittent MemoryError persists.
