- (decision) Feature: render next 3 upcoming events in the reserved band at the bottom of the Clock screen (src/ui/clock_view.py), below the recentered clock and corner date rows. Decided via bmad-party-mode design session + confirmed mockup (https://claude.ai/code/artifact/263328da-aad8-4b48-9c06-c92ed3e8671e).
- (decision) Corner-row redesign (today top-left, luna-today top-right, clock recentered) already shipped in a prior commit; this spec covers only drawing into the previously-reserved, currently-empty band.
- (capability) CAP-1 intent: user glances at the Clock screen and sees their next up-to-3 upcoming events without leaving the clock view. success: with N>=3 real/simulated upcoming events queued, the Clock screen renders exactly 3 rows each as time + title; with N=1 or 2, exactly N rows render and no placeholder text fills the rest; with N=0, the band renders nothing (no heading, no empty-state text).
- (constraint) Each event row is exactly one line: 'HH:MM Title', FONT_SETTINGS_STATUS scale (16px), COLOR_SECONDARY, left-aligned at CLOCK_CORNER_PAD_X_PX — no per-row fill/badge box (that styling is reserved for the unsynced-clock alert, per prior design decision).
- (constraint) Rows must fit within the existing reserved geometry, config.CLOCK_EVENTS_BAND_H_PX = 56px at y=184..240 on the 320x240 ILI9341 screen — no change to clock or corner-row layout math in _layout().
- (constraint) Long titles must be measured (display.measure_text) and truncated with ellipsis to fit inside the row width — never overflow past x=310 or wrap to a second line.
- (constraint) Must follow the existing dirty-region redraw discipline in ClockView (cache dict, full vs partial redraw) — events band participates in _full_redraw's cache-and-compare, not a separate uncoordinated draw path.
- (non-goal) Non-goal: sourcing/syncing event data (ICS import, calendar API, manual entry UI) is out of scope for this spec — see open question on data source.
- (non-goal) Non-goal: tapping/selecting an event row, event details view, and multi-day/all-day event handling are out of scope for this pass.
- (question) What is the data source for 'upcoming events'? No Event model or event data source exists yet in src/calendar/ (only CalendarAnnotation/DayCell/MonthGrid for the month-grid view, gregorian/lunar date math — no event list, no ICS/API sync). This spec assumes an events-provider interface will be supplied or stubbed; the concrete source is unresolved and blocks a real (non-simulated) demonstration of CAP-1's success signal.
- (assumption) Assumed events are already sorted soonest-first and pre-filtered to 'upcoming' (not past) by whatever supplies them to ClockView — this spec's renderer takes a list of up to 3 already-selected events, not a raw event store.
- (note) Reference: touch-screen upgrade party-mode memlog (installed party) covers the earlier settings-screen/bottom-bar redesign; unrelated to this band but same screen family and constant-naming convention (CLOCK_* in src/config.py).
- (event) Self-validate pass 1 (coherence): PASS. CAP-1 has intent+success; intent is WHAT not HOW; all 4 constraints each rule something out; 2 non-goals present; success signal concrete/testable; 1 stable unique ID (CAP-1); prose lean.
- (event) Self-validate pass 2 (preservation): PASS.
