topic: Setup-AP and admin-page HTML/CSS/JS redesign to fix Pico W on-device MemoryError

- (note) Overrides part of wifi-config PRD (_bmad-output/planning-artifacts/wifi-config/prds/prd.md) and its EXPERIENCE.md UX spec, both already implemented in src/device/web/. This spec covers only the page-rendering layer (HTML/CSS/JS) and a new static-asset route; Wi-Fi join/KDF/session/coordinator logic is unaffected.
- (constraint) Root cause forcing this change: RP2040 (Pico W) has ~160-190KB usable MicroPython heap with a non-compacting mark-sweep GC; page_setup_content.py's ~4.3KB JS + ~1.8KB CSS causes intermittent on-device MemoryError, confirmed via hardware reproduction and community research this session (.temp/feeder-vs-pi-calendar-wifi-setup.md, .temp/page-redesign-proposal.md).
- (constraint) Setup-AP page (src/device/web/page_setup_content.py) MUST stay fully self-contained, no CDN or external asset reference: confirmed against src/device/network/coordinator.py that MODE_SETUP_AP runs the device's own isolated AP (network.AP_IF) with no upstream WAN route for the connecting client.
- (constraint) Login/settings pages (page_login_content.py, page_settings_content.py) only serve under MODE_STATION_ONLINE, confirmed only reachable after STA_IF joins the home Wi-Fi (coordinator.py lines 369, 956) -- so the browser here has real internet access, making a CDN reference viable for these two pages only.
- (direction) User (Minh) confirmed: use CDN approach for login/settings pages, keep site as minimal as possible while balancing UI/UX. User explicitly asked for override to be traceable against the existing wifi-config PRD/UX docs rather than silent.
- (capability) CAP-1 intent: setup-AP page (page_setup_content.py) renders as a plain server-rendered multi-step HTML form instead of a client-side JS SPA flow (no fetch, no in-place DOM rendering). GET / runs the Wi-Fi scan server-side and renders results as a native <select>; Rescan is a plain link causing a full-page reload back to GET /; submit is a plain <form method=POST action=/connect> full-page-reload using the already-existing response_join_success/response_join_failure renderers. success: page_setup_content.py's JS drops from ~4.3KB to under 1KB (0KB if the optional password show/hide toggle is also dropped) and CSS drops from ~1.8KB to under ~0.4KB; device serves the setup flow (scan, select, submit, connecting/success/failure states) without any client-side fetch/DOM-render code; repeated hardware soak test (cold boot + curl/browser walkthrough of the full setup flow) shows no web_construct_memory/web_asset MemoryError across at least 10 consecutive cold boots.
- (capability) CAP-2 intent: login/settings pages (page_login_content.py, page_settings_content.py) stop duplicating their shared CSS/JS inline in Python string constants and instead source it from one minimal, CDN-hosted classless CSS approach chosen to keep the rendered site as small/minimal as possible while remaining visually usable (balance UI/UX per user direction), used only in MODE_STATION_ONLINE where the browser has real internet access. success: page_login_content.py and page_settings_content.py no longer contain two duplicate copies of _CONFIG_CSS; total on-device Python source for these two modules' style/script footprint shrinks measurably (baseline: current combined _CONFIG_CSS+_LOGIN_JS+_SETTINGS_JS literal size); pages remain visually usable (form fields, buttons, accordion settings row) when rendered with the new minimal approach.
- (capability) CAP-3 intent: a new GET /static/<name> route exists only if the CDN choice for CAP-2 still needs any device-served static asset (e.g. a tiny local override stylesheet); if CAP-2 is satisfied purely by an external CDN reference with no local asset needed, CAP-3 is not required and should be marked not-applicable during implementation. success: if implemented, the route reads a file once from device flash and serves it with a long Cache-Control header, added in src/device/web/router.py, and is exercised by at least one host test.
- (decision) CAP-3 (new static-asset route) retracted: user confirmed a straight external CDN reference (e.g. classless CSS framework <link>) for CAP-2, which needs no device-served static asset at all, so no new router.py route is required. Superseded by this entry; CAP-3 id retired, not reused.
- (constraint) CDN choice must be a classless/minimal CSS-only framework (e.g. Pico.css/Water.css class), not jQuery or a JS-heavy library -- no page in scope does DOM manipulation heavy enough to justify a JS library payload; keep JS footprint on login/settings pages at or near zero, matching user's 'keep the site minimal' direction.
- (assumption) Exact CDN provider/URL and CSS framework choice (e.g. Pico.css vs Water.css vs another classless framework) left to implementer, constrained to: classless, CSS-only (no required JS), small (well under the ~1.8KB _CONFIG_CSS it replaces is not a hard requirement, since it is fetched once and cached, but should not be materially larger than the content it replaces).
- (assumption) Password show/hide toggle JS on setup-AP page (~15 lines) may be kept or dropped at implementer discretion; not load-bearing for CAP-1's success signal.
- (note) Override traceability against wifi-config PRD/EXPERIENCE.md: EXPERIENCE.md line 14 already specifies 'plain HTML/CSS/minimal JS' as intent for the Device's setup surface, so the shipped ~4.3KB JS SPA-like fetch/scan/banner flow is itself a drift from that original intent; CAP-1 restores that intent rather than purely overriding it. The concrete behavior change vs. the shipped implementation (not vs. the original UX intent) is: no-full-page-reload interactions (live rescan without reload, inline connect banner without navigation) become full-page-reload interactions. EXPERIENCE.md's substantive UX requirements -- status banner visible during connecting/failure, form field retention on failure (wifi password cleared, admin password kept), manual (non-auto) Rescan action, aria-live announcements -- are preserved via server-side re-render using the already-implemented response_join_failure/response_join_success prefill mechanism in src/device/web/pages.py, not dropped.
- (note) Non-goals: this spec does not change the Wi-Fi join/KDF/session/coordinator logic (src/device/network/coordinator.py join flow, PBKDF2 KDF, session table); does not change validation.py/verifier.py; does not add offline-caching or service-worker behavior for the CDN asset; does not redesign visual branding beyond what's needed for the minimal/classless treatment; does not change the fixed logging-dedup bug in coordinator._web_failure (tracked separately, not part of this page-rendering spec).
