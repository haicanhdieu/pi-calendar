## Intent

**Problem:** Multiple alerts due in one local minute, or while another alert is active, must not create duplicate audible occurrences or require duplicate user actions.

**Approach:** Keep one active occurrence in `App`, merge newly due alert members into it, and preserve its original sound and auto-stop lifecycle while rendering the combined count and resolving all captured members together.

## Boundaries & Constraints

**Always:** Use pure local-minute scheduling; deduplicate alert identities; preserve the first occurrence start/deadline; run one buzzer tick per loop; resolve every joined member through existing Stop, Postpone, and auto-stop paths; keep repeating alerts enabled and disable only joined one-time alerts.

**Never:** Create a second active occurrence or restart its buzzer/deadline; alter base alert configuration when joining; implement Story 2.7 configuration-commit semantics; import device modules into pure alert logic.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| SAME_MINUTE | Two enabled alerts match one local minute | One active occurrence contains both ids and one buzzer start | No duplicate member ids |
| ACTIVE_JOIN | One active occurrence, another alert becomes due | Existing occurrence gains member; start ticks and deadline stay unchanged | Continue current cadence |
| TERMINAL_RESOLUTION | Combined occurrence receives Stop, Postpone, or auto-stop | Every member resolves through existing terminal path | Missing/deleted ids tolerated |

</intent-contract>

## Code Map

- `src/alert/scheduler.py` -- returns all newly due alert records for one local minute and tracks per-alert raised keys.
- `src/alert/runtime.py` -- owns active occurrence creation, active-loop evaluation, buzzer ticking, postponement, and terminal resolution.
- `src/app.py` -- invokes alert evaluation before normal surfaces, keeping alert state single-writer.
- `src/ui/alert_view.py` -- renders count only when occurrence has more than one member; existing support is reusable.
- `tests/test_alert_scheduler.py` -- scheduler same-minute and per-alert deduplication coverage.
- `tests/test_alert_app.py` -- active joining, count rendering, unchanged deadline/cadence, and combined terminal behavior.

## Tasks & Acceptance

**Execution:**
- `src/alert/runtime.py` -- evaluate newly due alerts while active and merge unseen members without resetting lifecycle -- combine collisions into one occurrence.
- `tests/test_alert_scheduler.py`, `tests/test_alert_app.py` -- cover same-minute, active join, count, lifecycle, and terminal resolution -- prove host-observable behavior.
- `_bmad-output/implementation-artifacts/alert-clock/stories/2.6-alerts-that-collide-join-one-occurrence.md` -- record verification and final status.

**Acceptance Criteria:**
- Given two enabled alerts due in the same local minute, when scheduler evaluates, then one occurrence contains both and one buzzer cadence starts.
- Given an unanswered active occurrence, when another enabled alert becomes due, then it joins without restarting cadence or extending the five-minute deadline.
- Given a combined occurrence, when rendered, then `N ALERTS` appears for N greater than one and no count appears for one.
- Given a combined occurrence, when Stop or auto-stop resolves it, then every joined alert resolves under existing repeating/one-time rules.
- Given a combined occurrence, when Postpone defers it, then all members share one due time and re-alert as one combined occurrence.

## Design Notes

Active evaluation must happen before terminal handling changes state. Newly due members are computed from the same scheduler using current settings, filtered against current occurrence ids, then appended. The original `local` and `_alert_started_ticks` remain untouched; the existing single `buzzer.tick(now, True)` call continues.
