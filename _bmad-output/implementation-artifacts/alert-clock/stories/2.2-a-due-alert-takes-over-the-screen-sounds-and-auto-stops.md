## Intent

**Problem:** Configured alerts currently have no scheduler or active TFT presentation, so a due alert cannot interrupt normal rotation or produce bounded audible attention.

**Approach:** Add a pure local-civil-time scheduler and App-owned active occurrence. App captures due members, takes exclusive rendering ownership, ticks the injected buzzer once per loop, and resolves the occurrence after five monotonic minutes.

## Boundaries & Constraints

**Always:** Use retained `TimeSnapshot.local`; key base raises by `(alert_id, local_date, hour, minute)`; never retrofire the boot minute; keep scheduler/UI free of hardware imports; use wrap-safe ticks; preserve unsynced badge; use exact uppercase labels and fixed 25/50/25 bands; silence before terminal return; disable one-time alerts only when their ids still exist in canonical settings.

**Never:** Do not add Stop or Postpone touch actions, collision joining beyond capturing same-pass due members, postponed persistence, live config event application, failure UI, or device-validation claims.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Due | Local minute advances to enabled matching alert | One active occurrence and buzzer start | No duplicate key in same or revisited minute |
| Boot minute | First scheduler evaluation already matches | No raise | Establish baseline only |
| Invalid time | No local snapshot | No raise | Remain idle |
| Auto-stop | Active occurrence reaches 300000 monotonic ms | Silence, return to rotation, one-time disable | Preserve repeating alerts; log bounded persistence failure |

</intent-contract>

**Acceptance Criteria:**
- Given an enabled weekday alert and matching retained local minute, when App evaluates, then one active occurrence raises and normal rotation pauses.
- Given the first evaluation at a matching minute, when scheduler boots, then it does not retrofire; repeated or backward revisited keys do not raise again.
- Given an active occurrence, when each loop runs, then buzzer tick runs once and active alert remains exclusive.
- Given five monotonic minutes since raise, when App evaluates, then buzzer silences, active state ends, normal rotation resumes, and existing repeating settings remain intact.
- Given a one-time occurrence auto-stops, when terminal handling runs, then its existing canonical record is disabled without recreating deleted ids.
