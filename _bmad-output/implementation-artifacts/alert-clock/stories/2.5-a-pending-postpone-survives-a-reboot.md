<intent-contract>

## Intent

**Problem:** A postponed occurrence currently exists only in RAM, so reboot or power loss silently cancels a deliberate defer.

**Approach:** Store one normalized pending occurrence in the canonical SettingsStore record with its member alert identities and local due time. Restore only future due times; atomically clear resolved or overdue state.

## Boundaries & Constraints

**Always:** Keep SettingsStore as sole persistence boundary; preserve Wi-Fi, admin, alerts, and delay fields; use a versioned migration for existing records; commit complete records atomically; tolerate deleted member ids; compare local civil minute keys so overdue restore never rings; keep pure alert logic free of device imports.

**Never:** Add a second persistence file; recreate deleted alerts; retrofire overdue state; alter base alert configuration when postponing; implement collision behavior from Story 2.6 or live configuration semantics from Story 2.7; claim device validation from host tests.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| ACCEPT | Active occurrence and valid postpone | One atomic record contains future due local time and captured member ids | Preserve unrelated canonical fields; leave runtime recoverable on commit failure |
| FUTURE_REBOOT | Canonical pending occurrence due after restored local minute | App restores it and raises through existing active flow at due minute | No duplicate raise before due |
| OVERDUE_REBOOT | Canonical pending occurrence due at or before restored local minute | Pending field is cleared atomically; no buzzer sound | Base alerts remain unchanged and can fire later |
| TERMINAL_CLEAR | Pending occurrence reaches active state and Stop/auto-stop resolves it | Same canonical record commit clears pending field | Deleted member ids tolerated; delete wins |
| ATOMIC_FAILURE | Pending commit or clear fails | Existing valid record remains usable; no partial pending state | Log bounded secret-free failure; retry/recover on later action |

</intent-contract>

**Acceptance Criteria:**
- Given a valid postponed occurrence, when postpone is accepted, then one atomic canonical settings commit stores due local date/time and captured member ids while preserving Wi-Fi/admin/base alerts/delay.
- Given pending due time strictly in the future, when App boots and evaluates time, then it restores the occurrence and raises normally at due time without early sound or duplicate raise.
- Given pending due time at or before restored local minute, when App boots, then it clears pending atomically without sounding and leaves base alerts unchanged.
- Given pending occurrence resolves by Stop or auto-stop, when terminal transition commits, then pending state is cleared and later boot restores none.
- Given a captured member was deleted, when pending state restores or resolves, then no error occurs and deleted alert is not recreated.

## Spec Change Log

## Design Notes

Use a next canonical settings version so existing version-2 alert records remain readable through an atomic migration with `pending_postponed_occurrence: null`. Pending data is a compact immutable snapshot: due local civil fields plus member alert ids and member alert metadata needed by terminal resolution. Store validation must reject malformed pending data rather than partially load it. Runtime persistence failures must not destroy the in-memory occurrence; clear only after successful commit.
