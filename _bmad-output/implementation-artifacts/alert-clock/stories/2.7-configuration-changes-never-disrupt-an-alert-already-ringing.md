## Intent

**Problem:** Web configuration commits can occur while an alert is active or postponed. Runtime must not replace an occurrence's already-due members or interrupt its lifecycle because settings changed.

**Approach:** Refresh committed settings at each alert-loop boundary for future scheduling, while active and postponed occurrence records retain copied member data until terminal resolution.

## Boundaries & Constraints

**Always:** Apply the latest atomically committed settings before each scheduler evaluation; preserve active start/deadline, cadence, postponed due time, and captured member records; keep pure alert logic free of hardware imports.

**Never:** Re-read configuration to rewrite active or postponed members; reset an active buzzer/deadline after a commit; expand scope into failure recovery or device validation.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|---|---|---|---|
| ACTIVE_CONFIG_COMMIT | Active occurrence, store commit edits/deletes its alert | Existing captured member remains active with unchanged start/deadline; latest config drives only future due evaluation | Missing/deleted ids tolerated at terminal resolution |
| ACTIVE_NEW_MEMBER | Active occurrence, store commit adds another alert due next loop | New committed alert joins once at loop boundary without restarting cadence | Duplicate ids are ignored |
| POSTPONED_CONFIG_COMMIT | Postponed occurrence, store commit edits/deletes its alert | Captured member and due time remain unchanged; occurrence re-alerts from captured data | Current config used only for unrelated future scheduling |

</intent-contract>

**Acceptance Criteria:**
- Given an active occurrence, when alert configuration is committed, then its captured members, start tick, deadline, and buzzer cadence remain unchanged.
- Given an active occurrence, when a newly committed alert becomes due on a later loop, then it joins from latest settings without restarting the occurrence.
- Given a postponed occurrence, when its source alert is edited or deleted, then captured members and due time remain unchanged until re-alert or terminal resolution.
- Given committed settings are available at a loop boundary, when future scheduling runs, then it uses latest settings rather than boot-time settings.

## Design Notes

`SettingsStore.commit()` updates its canonical cache atomically. Runtime should read that cache at the start of each `evaluate()` call, then use the refreshed dictionary only for scheduler input and future persistence. Active/postponed dictionaries already contain copied alert records; do not rebuild them from refreshed settings.
