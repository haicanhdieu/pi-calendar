<intent-contract>

## Intent

**Problem:** The authenticated Config page displays the global postpone delay but provides no way to change it. Owners need one persisted delay used by later postpone actions.

**Approach:** Add an inline authenticated whole-minute control in the existing POST settings flow. Validate 1–60 strictly, preserve alerts and all unrelated settings, and commit the complete canonical record atomically through SettingsStore.

## Boundaries & Constraints

**Always:** Keep one canonical `postpone_delay_minutes` value in the version-2 settings record; require authenticated mutation; preserve Wi-Fi, admin, color, and alert fields; keep validation pure and CPython-compatible; show current value and unit clearly; return success or inline range feedback.

**Never:** Add a second persistence file or duplicated runtime constant; accept fractions, zero, values above 60, or non-numeric input; modify alert records; implement Epic 2 scheduling, postpone execution, or TFT behavior.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| HAPPY_PATH | Authenticated POST with `postpone_action=save` and `postpone_delay_minutes=15` | Same complete record committed atomically with delay 15; settings page shows 15 minutes and success confirmation | No error expected |
| DEFAULT | Authenticated v2 record with delay 10 | Config page shows numeric value 10 and visible minutes unit | No error expected |
| INVALID_RANGE | Authenticated POST with 0 or 61 | Record unchanged; page shows accepted range 1 to 60 whole minutes | Inline danger feedback |
| INVALID_FORMAT | Authenticated POST with fraction or non-numeric text | Record unchanged; page shows accepted range 1 to 60 whole minutes | Inline danger feedback |
| UNAUTHENTICATED | POST without valid session | Existing login redirect; record unchanged | Authentication rejection |
| COMMIT_FAILURE | Valid form with atomic store failure | Record remains unchanged and bounded save error is shown | Inline/server error |

</intent-contract>

**Acceptance Criteria:**
- Given an authenticated Config page with no custom delay, when it renders, then `POSTPONE` shows a whole-minute control labeled `Postpone delay (min)` with value 10.
- Given an authenticated control, when 15 is saved, then one atomic SettingsStore commit persists `postpone_delay_minutes` 15, preserves alerts and unrelated settings, and the response shows a success confirmation.
- Given an authenticated control, when 0, 61, a fraction, or non-numeric text is submitted, then the response names the accepted range 1 to 60 whole minutes and the stored record is byte-for-byte unchanged.
- Given no valid authenticated session, when the postpone mutation is posted, then existing authentication rejection occurs and no settings data changes.
- Given a stored delay of 15, when any existing Config page reads settings, then it reads 15 from the canonical record and displays the minutes unit.

## Design Notes

Use the same flat Config page and feedback treatment as alert mutations. Keep `postpone_delay_minutes` in every commit call so password and alert mutations cannot erase it; route validation must not allocate hardware modules.
