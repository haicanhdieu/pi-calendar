## Intent

**Problem:** A buzzer or alert-render failure must not terminate the cooperative clock loop or leave alert handling in an unrecoverable state. Diagnostics must identify the failed phase without exposing settings, credentials, or exception text.

**Approach:** Contain buzzer and alert-render failures at the alert runtime boundary, silence the buzzer best-effort, emit one bounded secret-free diagnostic per occurrence, and retry buzzer initialization for later alert occurrences.

## Boundaries & Constraints

**Always:** Alert evaluation remains non-blocking; active and postponed state remains coherent; buzzer failures are bounded and later alert attempts can recover; diagnostics use stable phase/code names only.

**Never:** Do not log exception messages, settings, credentials, alert payloads, or tracebacks; do not import hardware modules into pure logic; do not make device validation claims from host tests.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Buzzer failure | `tick()` returns failure or raises during active alert | Alert screen and loop continue; buzzer is silenced best-effort | One `alert_fail buzzer <code>` diagnostic; no secret data |
| Render failure | Alert view raises while alert is active/postponed | Loop returns normally and later touch/alert processing remains possible | One `alert_fail render <code>` diagnostic; no exception text |
| Later recovery | New occurrence after prior buzzer failure and port `initialize()` succeeds | Buzzer attempts cadence again | Fault state clears only after successful initialization |

</intent-contract>

## Code Map

- `src/device/buzzer_port.py` -- cooperative buzzer result codes and retryable `initialize()` contract.
- `src/app.py` -- calls alert evaluation from `step()`; must remain alive when runtime contains failures.
- `tests/test_alert_app.py` -- end-to-end host fixtures for active alert loop, rendering, and recovery.
- `tests/test_buzzer_port.py` -- stable buzzer failure result-code behavior.

## Tasks & Acceptance

**Execution:**
- `src/alert/runtime.py` -- add bounded wrappers for buzzer and alert-view operations, secret-free one-per-occurrence diagnostics, best-effort silence, and later-occurrence buzzer reinitialization -- keep failures inside cooperative loop.
- `tests/test_alert_app.py` -- test returned/raised buzzer failures, raised render failures, secret-free logs, loop continuation, and later buzzer recovery -- prove each edge case at outer app surface.

**Acceptance Criteria:**
- Given an active occurrence, when buzzer drive returns a failure or raises, then `App.step()` returns without raising, alert state remains resolvable, and diagnostic contains only `alert_fail buzzer <stable-code>`.
- Given an active or postponed occurrence, when alert rendering raises, then `App.step()` returns without raising and diagnostic contains only `alert_fail render <stable-code>`.
- Given a prior buzzer failure, when a later occurrence starts and initialization succeeds, then buzzer cadence is attempted again.
- Given any contained failure, when logs are inspected, then exception messages and alert/settings payloads are absent.

## Design Notes

Failure state is scoped to the current occurrence for render and sound suppression, while the port object remains available for a fresh initialization at the next occurrence. Control polling occurs before evaluation, so STOP/POSTPONE remain usable after a failed render.
