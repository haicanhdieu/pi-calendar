<intent-contract>

## Intent

**Problem:** Authenticated Config can add and edit alerts but cannot remove an obsolete alert. Owners need an explicit browser confirmation so an accidental click cannot delete a schedule.

**Approach:** Add a danger-styled Delete control to each alert editor. Browser confirmation gates a normal authenticated delete POST; the server validates the selected stable id, removes exactly one alert, and commits the complete remaining settings atomically.

## Boundaries & Constraints

**Always:** Require an authenticated session for delete POSTs. Require explicit browser confirmation before submission. Preserve all remaining alert ids and values, Wi-Fi/admin/color/postpone fields, and SettingsStore atomic-write semantics. Re-enable Add alert after deleting from a ten-alert record. Keep pure validation host-compatible and preserve bounded page/request behavior.

**Never:** Delete on GET or on a declined confirmation. Do not add a second persistence path, delete by array position, change alert scheduling/runtime behavior, or implement Story 1.5+.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| HAPPY_PATH | Authenticated delete for existing id | One matching alert removed; remaining record committed and rendered | No error expected |
| DECLINED | Browser `confirm()` returns false | No request and no mutation | Alert remains unchanged |
| UNKNOWN_ID | Authenticated POST with absent id | No mutation; settings page reports not found | Bounded 400 response |
| UNAUTHENTICATED | Delete POST without valid session | No mutation | Existing login redirect |
| COMMIT_FAILURE | Valid delete but atomic commit fails | No success result; prior settings remain observable | Bounded error response |

</intent-contract>
